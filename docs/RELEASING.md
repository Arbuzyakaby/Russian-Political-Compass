## Подготовка

Проверьте `git status`, текущую ветку и remote. Отделите файлы выпуска от существующих локальных материалов. Запишите фактически выполненные изменения; не переносите исправления прошлого выпуска в новый как новые возможности.

Для 3.1.1 сохраняется название «Висла» / “Vistula”. Дата выпуска — 26 октября 2026 года. Изменение номера приложения не требует изменения формата ссылок на результаты теста.

## Где обновлять версию

| Место | Что изменить |
| --- | --- |
| `package.json` | Точный машинный номер, например `3.1.1`. |
| `js/data.js` | `VERSION` с тем же номером; `VERSION_NAME` меняется только при смене названия. Подпись формируется из них. |
| `index.html` | Статическая подпись и подсказка в подвале, русский текст окна изменений. |
| `js/i18n-misc.js` | Подсказка версии и тексты `wel.up.*` на русском и английском. |
| `js/data-history.js` | Новая запись истории сайта с датой и двуязычным описанием. |
| `README.md`, `CHANGELOG.md` | Текущий выпуск и новая запись в начале журнала; прошлые записи сохранить. |
| Тесты | Явные ожидания текущего номера и подписи. |

Найдите остальные упоминания прошлого номера через `rg`. Различайте обозначение текущего выпуска, историческую запись, комментарий и числовое значение: глобальная замена недопустима.

Окно обновления сравнивает сохранённый `pc-welcome` с `PC.VERSION`. После закрытия оно запоминает новый номер. Для проверки используйте отдельный профиль браузера; не очищайте свои сохранённые результаты.

## Проверки перед выпуском

```sh
npm test
npm run test:visual
git diff --check
```

Для второй команды нужен отдельно установленный Playwright; см. [подготовку окружения](DEVELOPMENT.md#проверки).

- Проверьте подвал, окно изменений и историю на обоих языках и мобильном экране.
- Убедитесь, что предыдущая версия вызывает окно обновления, подтверждённая текущая — не вызывает, а ссылка на результат открывается без приветствия.
- Проверьте ссылки и изображения в README, команды запуска и актуальность руководств.
- Пересмотрите diff: никаких личных ответов, локальных отчётов, `node_modules` и случайных файлов.

## Коммит и тег

Добавьте в индекс только файлы релиза. Пример для уже проверенного выпуска:

```sh
git commit -m 'release: 3.1.1 «Висла»'
git tag -a 3.1.1 -m '3.1.1 «Висла»'
git push origin main
git push origin refs/tags/3.1.1
```

Перед созданием тега проверьте локальные и удалённые теги. Тег должен указывать на релизный коммит. Уже опубликованный тег не перемещайте и не отправляйте с `--force`; ошибочный выпуск исправляется отдельным согласованным обновлением.

## После отправки

Проверьте успешное завершение GitHub Actions для релизного коммита, наличие ветки и тега в remote, затем версию на публичном сайте. Текущий workflow репозитория проверяет модульные тесты; он сам по себе не подтверждает публикацию сайта. Способ публикации зависит от настроек хостинга.

Если коммит доставлен, а сайт ещё показывает старый номер, сообщите об этом отдельно. Не считайте успешный push доказательством завершённого развёртывания. GitHub Release создаётся только по отдельному запросу.
